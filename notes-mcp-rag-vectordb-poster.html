  • Server = dumb executor. It never talks to the LLM — it just runs whatever python function is registered.
  • @mcp.tool() reads the function's type hints + docstring → auto-builds a JSON Schema for it.
  • Client = the brain. It owns the LLM call and decides which tool (if any) to invoke.
  • Handshake: initialize() → list_tools() → (LLM picks) → call_tool().
In this repo: chat.py spawns server.py as a subprocess over stdio, on every run — it's not a daemon.

Vector DB meaning as coordinates

closer = more similar
↑ top-k neighbors
  • Embedding = text → list of floats (a point in high-dim space). Similar meaning ≈ nearby points.
  • Vector DB indexes those points for fast "nearest neighbor" search (cosine similarity here).
  • Stores the vector and a payload (metadata: title, section, source URL) alongside it.
  • Query = embed the question the same way → search → get the closest stored chunks.
In this repo: embeddings.py (SentenceTransformer, all-MiniLM-L6-v2, 384-dim) + vectorstore.py (Qdrant, collection stuttgart_bureaucracy).

MCP protocol internals

  • Transport is JSON-RPC 2.0. Three shapes: stdio (subprocess, implicit trust — no auth needed, this repo's case), SSE (legacy remote), Streamable HTTP (current remote transport, supports resumable sessions).
  • initialize() is a capability negotiation, not just a ping: client/server each declare what they support — tools, resources, prompts, sampling, roots, elicitation — and only the intersection is usable.
  • Sampling inverts control: a server can ask the client's LLM to generate a completion mid-tool-call (e.g. to summarize before returning). Not used here — this server only returns data, never calls back.
  • Elicitation: server can pause a tool call and ask the client to prompt the user for missing input (e.g. "which semester?") before continuing.
  • Tools can carry annotations (readOnlyHint, destructiveHint, idempotentHint) so a client can auto-approve safe calls and gate risky ones — worth adding here since both tools are read-only.
  • Long tool calls support progress notifications and cancellation; resources support subscribe/notify on change.
  • Security: tool descriptions are untrusted input to the LLM's context — a malicious/compromised server can smuggle instructions into a docstring ("tool poisoning" / rug-pull updates). Treat third-party MCP servers like you'd treat an unvetted dependency.
  • Remote (HTTP) servers authenticate via OAuth 2.1; the installed SDK (mcp>=2.0.0) also ships RequestStateSecurity/AESGCMRequestStateCodec for encrypted per-request state — irrelevant for a local stdio server like this one.

RAG production patterns

  • Hybrid search: combine dense (embedding) + sparse (BM25/keyword) retrieval, fuse with Reciprocal Rank Fusion — catches exact terms (form names, office names) that embeddings blur. This repo is dense-only.
  • Reranking: two-stage retrieval — cheap ANN search pulls top-50, a cross-encoder reranks to the true top-k. Higher precision than raw cosine similarity, at extra latency cost.
  • Query transformation: HyDE (embed a hypothetical answer instead of the raw query), query rewriting/expansion, or multi-query fan-out — helps when the user's phrasing doesn't match the doc's phrasing.
  • Contextual chunking: prepend a short LLM-generated summary of surrounding context to each chunk before embedding (Anthropic's "contextual retrieval") — mitigates chunks losing meaning in isolation.
  • Failure modes to know: lost-in-the-middle (LLM under-attends to context stuffed mid-prompt), plausible-but-wrong chunk retrieval, stale index vs. source drift, chunk boundaries cutting a fact in half.
  • Evaluation: recall@k / MRR for the retriever, faithfulness & context-precision (RAGAS-style) for the generated answer — not "does it look right," measured.
  • Agentic vs. naive RAG: this project already does the better pattern — retrieval is a tool the LLM chooses to call, not context force-injected every turn.

Vector DB index internals

  • HNSW (Hierarchical Navigable Small World) is Qdrant's default index — a multi-layer proximity graph. Key knobs: m (edges/node), ef_construct (build-time search width), ef_search (query-time width) — all trade recall for latency/memory.
  • Alternatives: IVF (cluster-then-search, used by FAISS/Milvus), product/scalar quantization to compress vectors in memory at some recall cost — matters once you're past ~millions of points, not at this repo's scale (a few dozen chunks).
  • Cosine vs dot-product vs Euclidean: if vectors are L2-normalized (this repo's embed_texts(..., normalize_embeddings=True)), cosine similarity and dot product become equivalent — dot product is cheaper to compute.
  • Filtering: combine metadata filters (topic, date) with vector search — pre-filter (restrict candidates first) vs post-filter (search then discard) changes both recall and speed. Payload here (title, section, source) is stored but never filtered on.
  • Zero-downtime reindex: production pattern is build a new collection, then swap a collection alias. This repo's ensure_collection() does delete-then-recreate — fine at dev scale, but is a brief window of zero results if it ran against live traffic.
  • Named/multi-vectors: a single point can hold several vectors (e.g. dense + sparse, or one per field) for hybrid search — this repo stores exactly one dense vector per chunk.
  • Durability: WAL + periodic snapshots for backup/recovery — relevant once qdrant_storage/ holds something you can't just regenerate from data/docs/.
